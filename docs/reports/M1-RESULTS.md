# M1 实现与验证结果

日期：2026-11-09。最终目标为 Limbus Company；本轮完成其前置终端传输原型，未运行游戏，也未实现 Wine 驱动。

## 交付

- `winetk-terminal-demo`：独立 C 程序，默认 640×360 / 15 fps 提交上限，RGBA 整帧直接传输，不放大画布；终端较小时等比缩小并使用同一坐标映射。
- 可替换后端接口与 Kitty 实现，支持 stride、有效缓冲范围检查、4096 字节 Base64 分块、稳定 placement 和仅清理自身 image。
- 流式输入解析：Kitty 键盘按下/重复/释放与关联文本、UTF-8、SGR 鼠标、focus、粘贴、图形/尺寸/模式应答。输入和图形协议响应共用一个解析器。
- 控制 TTY 独占、分阶段模式切换、信号处理、限时写入、无积压补帧；异常路径取消残留序列并恢复自己改变的状态。
- JSONL 指标与事件；可选限量 PNG 源帧与实际图形输出字节记录。

使用入口与字段解释见 [TERMINAL-DEMO.md](../TERMINAL-DEMO.md)。未修改系统 Kitty 或用户现有终端配置。

## 自动验证

GCC 16.2.1 的 RelWithDebInfo 构建与 Clang 23.1.4 的 Debug + ASan/UBSan 构建，均启用 `-Wall -Wextra -Wpedantic -Werror`。
两种构建的 CTest 均检查三个测试目标：

| 目标 | 覆盖 |
| --- | --- |
| `input` | 全分割点/逐字节输入、协议交错、按键动作/Unicode/粘贴、鼠标/焦点、畸形与超长序列恢复、坐标留边/捕获边界 |
| `kitty` | 独立解码 Base64 对比像素、块大小、stride/裁剪、尾块、部分写入/EINTR/错误、尺寸溢出、固定 ID 与定向清理 |
| `demo_pty` | 8 个控制 TTY 场景：正常结束、增强 Ctrl+C、空闲 SIGTERM、首帧传输中 SIGTERM、延迟模式应答、仅字符像素尺寸时 resize、静默终端探测超时、TTY 断开 |

PTY 场景核验 termios、模式与图像清理、JSONL、PNG CRC/解压尺寸、录制数量上限以及 stdout/stderr 不混入图形流。
传输中 SIGTERM 在首个约 1.2 MB 图像的分块期间触发，确认没有完成帧记录、能中止上传并清理，退出码 143。
延迟模式应答不能让输入解码与实际启用的鼠标坐标模式分离；无像素 ioctl 字段时，字符尺寸回退能随 80×24 → 100×30 更新为 800×480 → 1000×600。
探测失败不会弹出调用方的键盘协议栈或进入备用屏。`--log` 拒绝 `/dev/full`、TTY、FIFO 等非普通文件，日志写入错误不会报告成功。

## 真实 Kitty 验证

在本机 Kitty 0.49.2 的独立测试实例中运行原型，使用该实例的 Unix socket 控制，不更改已有 Kitty 会话。
真实终端返回图形、键盘、像素鼠标和同步更新支持。

| 项目 | 结果 |
| --- | --- |
| 实际画布 | 截图（本地：`logs/m1-live-kitty.png`） 的非黑像素边界恰为 `(953,170)-(1593,530)`，对应 640×360 的居中画布 |
| 像素正确性 | 对照 `frame-000001.png`，截图标题区 640×48 和三色条静态区域逐像素完全相同，确认通道、位置与传输正确 |
| 键盘 | 通过 Kitty `send-key` 送入 Ctrl+A、方向键、Space，收到按下/释放并更新状态；Ctrl+C 正常退出，退出码 0 |
| 文本 | 通过真实终端子进程通道收到“终端测试”的四个 Unicode 码点 |
| resize | 实际调整 Kitty pane，尺寸从 2547×700 等变化至 1314×240；画布等比缩小为 426×240，见 缩小截图（本地：`logs/m1-live-downscaled.png`） |
| 鼠标协议 | 向真实子进程 TTY 注入 SGR 点击/拖动/释放/滚轮，缩小后的像素坐标正确映射到逻辑画布；完整动作与越界规则由自动测试检查 |
| 录制 | `logs/m1-live-capture/` 保存前三帧 PNG 及 3,698,412 字节 `graphics.bin`；程序继续运行不会无限保存像素帧 |

鼠标的受控动作验证使用协议注入，尚需用户在自己的常用终端布局中手动体验点击、拖动和 IME；这里不将注入测试当作完整物理输入设备兼容性证明。
Kitty 的截图来自终端实际渲染，区别于 producer 保存的 PNG；两者只比较静态区域，不用不同时间的动画帧冒充全帧一致。

## 第一份性能基线

取真实会话最初 500 次 640×360 提交；`--fps 15`，未启用压缩：

| 指标 | 实测 |
| --- | --- |
| 每帧输出 | 1,232,804 字节，含图形和同步控制序列 |
| 提交频率 | 约 12.27 fps（首末帧相隔 40.658 秒） |
| 对应传输量 | 约 15.13 MB/s（14.43 MiB/s） |
| 绘制 + 缩放中位耗时 | 4 ms |
| 编码 + 写入中位耗时 | 6 ms；此样本最大 118 ms |

这是原型进程提交链路的测量，不是游戏帧率或终端实际显示刷新率；读回/GPU 尚未参与，也未测端到端输入延迟。
当前为同步、限时直接传输，下一阶段先保持接口正确；压缩、共享内存和异步输出根据更大分辨率的测量再优化。
