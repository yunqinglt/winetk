# 东方红魔乡测试目标

本地 `game/` 是用户提供的《东方红魔乡》1.02f（2002-08-30），主程序为 i386 PE32。
该目录按原样保留，不作为游戏运行的工作目录；测试使用 `out/game-th06/` 副本、`prefixes/th06/` 独立 Wine 前缀。
不复制游戏内容到仓库，也不修改游戏可执行文件。

## 文件与配置准备

```sh
./scripts/prepare-th06.py
./scripts/run-th06.sh
# 限时测试，同一启动器还接受 --fps / --duration 等 run-wine.sh 参数
./scripts/run-th06.sh --duration 20
```

准备脚本会拒绝覆盖已有目标。再次运行启动器会沿用已有副本，保存游戏生成的配置、存档和日志。
需要另一个实验副本时：

```sh
./scripts/prepare-th06.py --destination out/game-th06-muted --mute
WINETK_TH06_DIR="$PWD/out/game-th06-muted" ./scripts/run-th06.sh --duration 20
```

`--mute` 只在副本中关闭音乐和音效。
普通启动保留用户原来的输入和音频配置。参数位于启动器的 `--` 之前，由 `run-wine.sh` 处理。

原始文件名 `搶曽峠杺嫿.exe`、`峠杺嫿ST.DAT` 等是 CP932 字节被当作 GBK 解码后的结果。
准备脚本仅对程序、配置和六个已知数据归档做可逆转换：`name.encode('gbk').decode('cp932')`，恢复为
`東方紅魔郷.exe`、`東方紅魔郷.cfg`、`紅魔郷{CM,ED,IN,MD,ST,TL}.DAT`。
随游戏的启动 BAT 解码为 CP932 后直接写着 `start 東方紅魔郷.exe`，与修复结果一致。
日文手册和其他原本正确的文件名保持原样。

副本中的 `.winetk-th06.json` 记录原始文件 SHA-256、文件名映射及配置修改前后的完整十六进制内容。
准备后已对原始文件重新计算 SHA-256，确认与记录一致。

配置大小为 `0x38`，`0x14` 处版本值为 `0x102`；不符合时拒绝修改。
根据 [TH06 逆向源码 GameConfiguration](https://github.com/happyhavoc/th06/blob/master/src/Supervisor.hpp)，
`0x1e` 是 windowed，`0x1f` 是 frameskipConfig。
准备时设 windowed=1、frameskipConfig=0；用户给定原始配置本来已经是这两个值。
游戏逻辑画面为 640×480。

`0x34` 的 32 位选项 bit 11 在较新版本中称为 dontUseDirectInput，但
[SetupDInput 的版本条件](https://github.com/GensokyoClub/th06/blob/master/src/Supervisor.cpp) 明确从 1.02g 才检查此位。
本机的 1.02f 不支持用它关闭 DirectInput；准备脚本的 `--no-directinput` 会报错且不创建副本。
早期 `out/game-th06-polling/` 实验副本曾设置此位，该副本不能作为键盘轮询回退的证据。

启动器通过 `localedef --no-archive` 生成项目内的 `out/locales/ja_JP.UTF-8/`，只给该会话设置 `LOCPATH` 和
`LC_ALL=ja_JP.UTF-8`。这使 Wine 为旧 ANSI 日文路径提供 CP932，不改变系统 locale 或用户其他前缀。
Wine 11.19 的 ANSI 码页从 Unix 系统 locale 推导；仅修改注册表 ACP 不足以替代这个步骤。

## 图形与输入要求

`objdump -p game/搶曽峠杺嫿.exe` 显示主程序直接导入：

| DLL | 入口或用途 |
| --- | --- |
| `d3d8.dll` | `Direct3DCreate8`，游戏图形走 Direct3D 8 |
| `DINPUT8.dll` | `DirectInput8Create`，默认键盘/手柄输入 |
| `DSOUND.dll` | DirectSound 音频 |
| `WINMM.dll` | 定时器、WAV/MIDI |

因此 GDI 转发成功并不能代表该游戏可运行；需要 WineD3D → 离屏 OpenGL/EGL → 窗口图像读回路径。
手册与 `readme.txt` 同样说明需要 DirectX 8.0，支持 32/16 位颜色、窗口/全屏、绘制间隔及 60 FPS 设置。
它比 Unity 目标简单，但仍是真正的 Direct3D 固定管线游戏。

## 最小 D3D8 验证程序

```sh
./scripts/build-smoke.sh
./scripts/run-wine.sh --fps 60 -- "$PWD/out/smoke/d3d8-window-i386.exe" --duration 8
```

`tests/smoke/d3d8-window.c` 创建 640×480 D3D8 窗口，以 60 FPS 目标绘制 RGB 顶点插值三角形与深蓝底色。
它记录 CreateDevice 结果、实际 Present 数、键盘和点击计数，可使用 `--status PATH` 输出 JSON。
使用动态加载 `d3d8.dll`，兼容本机没有 `libd3d8` 导入库的 MinGW 工具链。
与 GDI 和 WGL 样例一起构建 i386、x86-64 两种架构；游戏验收以 i386 为准。

## 本轮真实验证

真实游戏已经通过 WineD3D → surfaceless EGL → RGBA/IPC → Kitty 显示到终端。
中途截图（本地：`logs/m3-th06-running.png`） 显示角色/符卡选择画面、无 Wine 标题栏的 640×480 图像，以及首行 `東方紅魔郷.exe`。
该截图的游戏内计数为 35.57 FPS；初期约 35–40 FPS 的结果用于定位同步读回、broker 和终端传输瓶颈，**不作为最终性能结果**。后续优化和最终游戏验收统一见 [本轮结果](reports/M3-RESULTS.md)。

方向键曾因 Windows VK → 扫描码映射落到数字小键盘而无法正确控制 DirectInput 游戏。
驱动已为增强导航键显式发送物理 E0 扫描码。为避免仅靠界面变化推断，新增真实 `DirectInput8Create` / `GetDeviceState` 测试：

```sh
./scripts/build-smoke.sh
python3 tests/test_dinput_live.py --arch i386
```

实际 i386 验证记录位于 `logs/m3-dinput-live/i386/`：10.008 秒内 992 次成功键盘轮询；Kitty 增强协议分别按住并释放四个方向键，
`DIK_UP/DOWN/LEFT/RIGHT` 各产生一次按下且都有多个持续按住样本；`DIK_NUMPAD8/2/4/6` 的计数与样本全部为零，四个方向最终均已释放。
普通游戏副本保留默认 DirectInput。
测试使用约 250 ms 的实际按住事件，未使用同一瞬间按下/释放来替代游戏状态轮询。

这项早期测试使用了手动构造的 CSI-u 方向键，随后又发现真实 Kitty 编码路径中的独立问题：即使已经启用事件类型报告，
Kitty 的方向键按下仍然可以是 `ESC[A`，重复为 `ESC[1;1:2A`，释放为 `ESC[1;1:3A`。
解析器把这些功能键语法统称为 legacy，而会话对 legacy 按下立即合成释放，导致记事本能收到消息、轮询状态的游戏却看不到持续按住。
现在带事件类型的功能键保留正确按下/重复/释放语义；终端启用增强键盘后，裸功能键按下也会保持到真实释放，只有未启用增强报告的兼容路径才合成立即释放。

最新实测覆盖了这个区别：

```sh
# 三条路径：Kitty 实际编码器、功能键 CSI、原有 CSI-u
python3 tests/test_dinput_live.py --arch i386
# 使用本机用户的 Kitty 配置，并由 Kitty 自己编码按住/重复/释放
python3 tests/test_dinput_live.py --arch i386 --kitty-config user --key-source kitty
```

`logs/m3-native-key-capture/{default,user}/bytes.json` 记录了默认配置与用户当前配置生成的相同方向键字节。
`logs/m3-dinput-functional-default/` 的三条路径和 `logs/m3-dinput-real-user/` 的用户配置路径均已通过：每个方向按住约 250 ms，
重复不产生额外按下跳变，DirectInput 有多个持续样本、最终释放，数字小键盘状态始终为零。
Kitty 编码器测试使用单独定时的 WindowSystemKeyEvent，让 Kitty 按当前协商模式生成字节；它不是把预先选定的 CSI 字节直接塞给应用。
普通 `kitten @ send-key` 会在同一操作中按下并释放，仍不能替代这项持续输入验收。

客户区/尺寸的真实 GDI 回归位于 `logs/m3-gdi-final/`，由 `tests/test_wine_live.py` 自动执行：

- x86-64 请求并实际得到 960×720，i386 为 640×400；样例未覆写 `WM_GETMINMAXINFO`。
- 画布与 Windows 返回的客户区尺寸一致；截图精确检查头部、正文和右下角的颜色，确认无非客户区标题栏，且大窗口未被旧 800×600 桌面裁掉。
- 两种架构均通过首次点击前键盘、中文粘贴、左右键、滚轮、首行文件名和退出状态检查；`strace connect` 记录含项目 socket，无 X11/Wayland 连接。

双架构 WGL 测试另已验证 640×480→800×600 resize、RGBA 通道与上下方向，约 100 FPS 的独立读回/IPC 并非真实游戏或终端帧率。
这些结果证明本轮涉及的显示/输入链路，尚不代表完整多窗口、所有 D3D8 游戏或 Unity/Limbus 的兼容保证。

最终完整构建使用 Vulkan 内存互操作修复 Wine WoW64 缓冲映射复制开销，图形仍由 surfaceless OpenGL 呈现。用户 Kitty 配置下的第一关、原生方向键编码已实测：约 59.32 FPS 终端提交，游戏自身约 62.50fps，角色能随方向键持续移动。截图与性能记录见 `logs/m3-th06-user-final/auto/` 及 [最终结果](reports/M3-RESULTS.md)。旧会话需要退出后重新运行 `./scripts/run-th06.sh`，才能载入新的终端程序和 Wine 模块。
